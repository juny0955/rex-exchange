이 문서는 `cancel-resting-order` 시나리오의 첫 기준선을 기록한다.
고정 측정 환경은 [Runtime Stress 위키 홈](../../../README.md)의 Vultr EPYC-Rome 환경을 사용한다.

## 요약

`cancel-resting-order` 단일 심볼 기준으로 200k commands/s까지는 채널 포화 없이 처리됐다.
300k부터 900k commands/s까지는 channel full이 소량 발생했지만 accepted/s와 published/s가 target/s에 가깝게 유지됐다.
950k commands/s 이상에서는 accepted/s가 크게 하락해 명확한 초과 구간으로 본다.

이 시나리오는 Place/Cancel 쌍으로 orderbook에 주문을 넣고 같은 주문을 제거한다.
체결 수와 maker 갱신 수는 모두 0이며, 반복 종료 시 orderbook이 비워지는 stationary 취소 경로 시나리오다.

| 항목 | 값 |
| --- | ---: |
| 안정 TPS | 200,000 commands/s |
| 경계 TPS | 300,000-900,000 commands/s |
| 초과 구간 | 950,000+ commands/s |

## 해석 포인트

- 100k, 200k는 채널 포화가 없으므로 안정권으로 본다.
- 300k부터 900k까지는 channel full이 소량 발생하므로 무손실 안정권은 아니지만 accepted/s는 target/s에 가깝다.
- 950k와 1,000k는 accepted/s가 크게 하락해 명확한 초과 구간이다.
- 주문 접수 결과와 주문 취소 결과가 거의 1:1로 발생하므로 Place/Cancel 쌍이 정상적으로 처리됐다.
- 체결 수와 maker 갱신 수는 모두 0이므로 이 결과는 matching sweep 비용이 아니라 orderbook 삽입/삭제와 cancel result 경로 비용을 본다.
- `completed = yes`는 접수된 command가 결과 발행까지 완료됐다는 뜻이다. channel full로 거부된 command가 처리됐다는 의미는 아니다.
