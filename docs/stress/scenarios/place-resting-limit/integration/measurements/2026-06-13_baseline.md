## 판정

- **안전 TPS = 25,000**. `채널 포화 0건`, `target 달성률 100%`이며 ack p99 `1.890ms`, E2E p99 `8.281ms`로 매우 안정적이다. commands/unit=1이라 batch RPC가 unary 대비 콜 수를 줄이지 못하므로, 다른 commands/unit=11 시나리오(안전 80k~100k)보다 훨씬 낮은 지점에서 안전 구간이 형성된다.
- **경계 TPS = 40,000**. `target 달성률 99.99%`는 유지하지만 `채널 포화 0.59%`가 발생하고 ack p99가 `1.890ms → 38.919ms`로 약 20배 급증한다. E2E p99도 `8.281ms → 45.087ms`로 동반 상승한다.
- **포화 TPS = 50,000**. `채널 포화 503은 0건`으로 유지되지만 `target 달성률 93.88%`로 부하 생성기가 목표 유입률을 따라가지 못한다(pacing 지연 누적 1,279,530s, 최대 1.852s). 즉 이 시나리오의 포화는 엔진 채널 백프레셔(503)가 아니라 **gRPC ack 처리 자체의 CPU 한계**(commands/unit=1 → unit마다 RPC 1콜, 콜당 고정비가 그대로 청구)로 나타난다. ack p99 `67.109ms`, E2E p99 `70.605ms`. `무손실 판정`은 여전히 통과(접수된 모든 이벤트는 15초 settle 내 수신).
- commands/unit=11 계열 시나리오(`full-fill-same-level`, `partial-fill-rest`: 안전 100k/경계 120k/포화 150k+, `market-quote-sweep`: 안전 80k/경계 100k/포화 130k+)와 비교하면, `place-resting-limit`은 batch RPC의 콜 절감 효과를 전혀 받지 못해 안전/경계/포화 구간이 약 1/2~1/3 수준으로 낮다. 또한 포화 양상도 503 기반이 아닌 **target 미달성(pacing 지연)** 형태로 다르게 나타난다.
